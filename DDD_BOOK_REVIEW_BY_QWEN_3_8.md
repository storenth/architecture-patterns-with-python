# 📖 ЧАСТЬ 1: РАСШИРЕННЫЙ ПЕРЕСКАЗ COSMIC PYTHON С ИНСАЙТАМИ ОТ ЭВАНСА

## 🔷 Глава 1: Domain Modeling — корни у Эванса (Ch 1, 2, 5)

### Что говорит Cosmic Python:
Бизнес-логика должна существовать как самостоятельная модель, свободная от инфраструктурных зависимостей.

### 🌳 Глубинные корни у Эванса:

**Chapter 1: Crunching Knowledge** — Эванс описывает процесс "переваривания знаний" через диалог с экспертами предметной области. Его знаменитый пример с **проектированием печатных плат (PCB)** показывает, как разработчик и эксперты вместе создают модель через постоянные уточнения.

**Chapter 5: Entities vs Value Objects** — Эванс вводит **фундаментальное различие**, которое Cosmic Python использует, но не объясняет глубоко:

#### 🎓 Для разработчика:

```python
# ENTITY — определяется идентичностью (продолжительностью во времени)
class Batch:
    def __init__(self, reference: str, sku: str, qty: int):
        self.reference = reference  # Идентичность!
        # Даже если все атрибуты изменятся, это тот же Batch

# VALUE OBJECT — определяется только атрибутами
@dataclass(frozen=True)
class OrderLine:
    orderid: str
    sku: str
    qty: int
    # Две OrderLine с одинаковыми атрибутами РАВНЫ
    # Они взаимозаменяемы
```

**Ключевой инсайт Эванса:** Identity — это **не техническая деталь** (не `id` в БД), а **концепция предметной области**. Два объекта могут иметь одинаковые атрибуты, но быть разными сущностями (два разных человека с одинаковым именем).

#### 🧒 Для школьника:

**Entity** — как ты сам. Даже если ты постригся, вырос на 5 см и сменил школу — ты всё равно **тот же самый человек**. У тебя есть "невидимая нить идентичности" от рождения до сейчас.

**Value Object** — как 100-рублёвая купюра. Тебе всё равно, какая именно бумажка у тебя в кармане — если она настоящая и на ней написано "100", ты можешь поменять её на любую другую такую же.

**Пример из Эванса (стр. 52):** Автор был ошибочно принят за должника-тёзку. Только проверка по телефонной книге за разные годы помогла доказать, что это **разные люди** (разные Entity), хотя имя и адрес совпадали!

## 🔷 Глава 2: Repository Pattern — корни у Эванса (Ch 6)

### Что говорит Cosmic Python:
Repository — это абстракция над хранилищем, коллекция объектов в памяти.

### 🌳 Глубинные корни у Эванса:

**Chapter 6: Repositories** — Эванс вводит Repository как способ **получить ссылку на уже существующий объект** в середине его жизненного цикла.

#### 🎓 Для разработчика — ключевые правила Эванса:

1. **Repository только для корней агрегатов** (не для внутренних объектов!)
2. **Иллюзия коллекции в памяти** — клиент не должен знать про БД
3. **Отделение от фабрик**: Repository находит старые объекты, Factory создаёт новые

```python
# ПЛОХО по Эвансу: прямой SQL в доменном слое
def get_customer_orders(customer_id):
    return db.execute("SELECT * FROM orders WHERE customer_id = ?", ...)

# ХОРОШО по Эвансу: Repository как коллекция
class CustomerRepository:
    def find_by_email(self, email) -> Customer:
        # Внутри может быть SQL, ORM, что угодно
        # Клиент видит только "дай Customer"
```

#### 🧒 Для школьника:

**Repository** — это как **гардероб в театре**. Ты говоришь: "Дайте моё пальто", и гардеробщик сам идёт искать его среди сотен других. Тебе не нужно знать:
- На какой вешалке оно висит
- В каком ряду
- Как гардеробщик запоминает номера

Ты просто получаешь **своё пальто обратно** — то же самое, что сдал.

**Инсайт Эванса:** Repository нужен **не для всех объектов**, а только для тех, которые являются "точками входа" (Aggregate Roots). Как ты не сдаёшь в гардероб каждый свой носок отдельно — так и Repository не нужен для каждого внутреннего объекта.

## 🔷 Глава 3: Abstractions — корни у Эванса (Ch 3, 10)

### Что говорит Cosmic Python:
Хорошая абстракция уменьшает связность (coupling), сохраняя согласованность (cohesion).

### 🌳 Глубинные корни у Эванса:

**Chapter 3: Binding Model and Implementation** — Эванс борется с идеей "отдельной аналитической модели". Он утверждает: **модель и код — это одно и то же**.

**Chapter 10: Supple Design** — Эванс описывает, как сделать дизайн "податливым":
- **Intention-Revealing Interfaces** — имена методов говорят "что", а не "как"
- **Side-Effect-Free Functions** — функции без побочных эффектов
- **Assertions** — явные контракты

#### 🎓 Для разработчика:

```python
# ПЛОХО: имя говорит "как"
def process_data(x, y):
    # нужно читать код, чтобы понять цель

# ХОРОШО (по Эвансу): имя говорит "что"
def calculate_shipping_cost(weight, destination):
    # Сразу ясно, что делает метод
    # Внутри может быть сложная логика, но интерфейс понятен
```

**Side-Effect-Free Functions** (Эванс стр. 158):

```python
# ПЛОХО: mixIn изменяет объект (side effect)
class Paint:
    def mixIn(self, other):
        self.volume += other.volume
        # ... сложная логика смешивания цветов
        self.color = ...

# ХОРОШО по Эвансу: новая VALUE OBJECT
class PigmentColor:
    def mixed_with(self, other, ratio) -> 'PigmentColor':
        # Возвращает НОВЫЙ объект, не меняет старый
        return PigmentColor(...)

class Paint:
    def mix_in(self, other):
        # Простая команда
        self.volume += other.volume
        self.color = self.color.mixed_with(other.color, ratio)
```

#### 🧒 Для школьника:

**Side-Effect-Free Function** — как **калькулятор**. Когда ты считаешь `5 + 3 = 8`, калькулятор не меняет ни пятёрку, ни тройку. Он просто даёт тебе ответ. Поэтому ты можешь спокойно использовать его снова и снова.

**Функция с побочным эффектом** — как **блендер**. Ты кладёшь туда фрукты, и они **исчезают**, превращаясь в сок. Ты не можешь "отменить" и получить фрукты обратно.

**Почему это важно:** Когда ты строишь сложную систему, функции без побочных эффектов — как безопасные кирпичики Лего. Ты можешь соединять их как угодно, не боясь, что что-то сломается.

## 🔷 Глава 4: Service Layer — корни у Эванса (Ch 4)

### Что говорит Cosmic Python:
Service Layer оркестрирует use cases, изолируя оркестрацию от бизнес-логики.

### 🌳 Глубинные корни у Эванса:

**Chapter 4: Layered Architecture** — Эванс описывает **четыре классических слоя**:

```
┌─────────────────────────────────┐
│   User Interface (Presentation) │  ← UI, API
├─────────────────────────────────┤
│   Application Layer             │  ← Service Layer у Perceval
│   (тонкий, только оркестрация)  │
├─────────────────────────────────┤
│   Domain Layer                  │  ← Модель, бизнес-логика
│   (сердце системы!)             │
├─────────────────────────────────┤
│   Infrastructure Layer          │  ← БД, email, API
└─────────────────────────────────┘
```

**Ключевой инсайт Эванса:** Application Layer **НЕ содержит бизнес-правил**! Он только координирует.

#### 🎓 Для разработчика:

```python
# ПЛОХО: бизнес-правила в application layer
def allocate_service(orderid, sku, qty):
    line = OrderLine(orderid, sku, qty)
    batch = repo.get(sku)
    if batch.available < qty:           # ← БИЗНЕС-ПРАВИЛО!
        raise OutOfStock()              #    должно быть в домене
    batch.allocate(line)

# ХОРОШО по Эвансу: правила в домене
class Product:  # Domain Layer
    def allocate(self, line):
        batch = self.find_available_batch(line)
        if not batch:
            raise OutOfStock()  # ← правило здесь
        batch.allocate(line)

def allocate_service(orderid, sku, qty, uow):  # Application Layer
    line = OrderLine(orderid, sku, qty)
    with uow:
        product = uow.products.get(sku=sku)
        product.allocate(line)  # ← просто делегируем домену
        uow.commit()
```

#### 🧒 Для школьника:

**Layered Architecture** — как **ресторан**:

- **Официант (Application Layer)** — принимает заказ, несёт его на кухню, приносит готовое блюдо. Он **не готовит**!
- **Повар (Domain Layer)** — знает рецепты, готовит по правилам. Это **сердце ресторана**.
- **Кладовщик (Infrastructure)** — привозит продукты, моет посуду.
- **Зал (UI)** — где сидят гости.

Если официант начнёт сам решать, сколько соли класть в суп (бизнес-правило), ресторан развалится. Каждый делает своё дело.

## 🔷 Глава 6: Unit of Work — корни у Эванса (Ch 6)

### Что говорит Cosmic Python:
UoW отслеживает изменения и сохраняет их атомарно.

### 🌳 Глубинные корни у Эванса:

Эванс говорит о **сохранении инвариантов** внутри транзакций, но UoW как паттерн описан у Мартина Фаулера. Однако Эванс вводит важную концепцию:

**Invariant** — правило, которое **всегда** должно быть истинным.

#### 🎓 Для разработчика:

```python
# Инвариант: сумма строк заказа не может превышать лимит
class PurchaseOrder:
    LIMIT = 10000
    
    def add_line_item(self, item):
        if self.total + item.price > self.LIMIT:
            raise LimitExceeded()
        self.items.append(item)
        # Инвариант: self.total <= self.LIMIT
        # ДОЛЖЕН быть истинным после каждой операции!
```

**Правило Эванса:** Инварианты должны соблюдаться **к концу транзакции**. Внутри транзакции они могут временно нарушаться.

#### 🧒 Для школьника:

**Инвариант** — как **правило в игре**: "у каждого игрока всегда должно быть ровно 7 карт". Во время хода у тебя может быть 6 или 8 карт (ты взял/сбросил), но **к концу хода** правило должно выполняться. Если нет — ты проиграл.

**UoW** — как **судья**, который следит, чтобы все правила соблюдались к концу раунда.

## 🔷 Глава 7: Aggregates — КЛЮЧЕВАЯ глава Эванса (Ch 6)

### Что говорит Cosmic Python:
Aggregate — кластер объектов, рассматриваемый как единое целое.

### 🌳 Глубинные корни у Эванса — это **его оригинальный паттерн!**

Эванс вводит Aggregate как решение проблемы **согласованности в сложных моделях**.

#### 🎓 Для разработчика — строгие правила Эванса:

1. **Корень агрегата (Root)** — единственная точка входа извне
2. **Внешние объекты могут держать ссылку ТОЛЬКО на корень**
3. **Внутри агрегата объекты могут ссылаться друг на друга**
4. **Удаление корня удаляет всё внутри**
5. **Инварианты обеспечиваются в пределах одной транзакции ТОЛЬКО внутри агрегата**
6. **Между агрегатами — eventual consistency (согласованность в конечном счёте)**

```python
# Aggregate Root
class Order:
    def __init__(self, id):
        self.id = id  # Глобальная идентичность
        self._items = []  # Локальная идентичность
    
    def add_item(self, product, qty):
        item = OrderItem(product, qty)  # Внутренний объект
        self._items.append(item)
        self._validate_total()  # Инвариант
    
    # ВНЕШНИЙ мир может вызвать только методы Order
    # Никто не может изменить OrderItem напрямую!

class OrderItem:  # ВНУТРЕННИЙ объект
    # Локальная идентичность — важен только внутри Order
    def __init__(self, product, qty):
        self.product = product
        self.qty = qty
```

**Пример Эванса (стр. 75-80):** Система заказов с лимитом. Если два пользователя одновременно добавляют строки в один заказ, инвариант "сумма ≤ лимит" может нарушиться. Решение — **блокировать весь агрегат** (Order), а не отдельные строки.

#### 🧒 Для школьника:

**Aggregate** — как **семья**:

- **Папа (Aggregate Root)** — единственный, с кем могут общаться посторонние. Если сосед хочет что-то передать, он говорит папе.
- **Мама, дети (внутренние объекты)** — общаются между собой свободно, но с внешним миром только через папу.
- **Семейные правила** — "нельзя тратить больше, чем есть в кошельке". Папа следит за этим.

**Важно:** Если две семьи (два агрегата) договорились о чём-то (например, дети ходят в гости друг к другу), они не могут гарантировать, что правила другой семьи соблюдаются **прямо сейчас**. Они доверяют друг другу.

## 🔷 Глава 8-10: Domain Events — ЭТОГО НЕТ У ЭВАНСА!

### Важное замечание:

Эванс в своей книге 2003 года **почти не говорит о событиях**. Эта концепция развилась позже, в основном благодаря:
- **Vaughn Vernon** ("Implementing Domain-Driven Design", 2013)
- **Udi Dahan** и другим экспертам
- **Event Sourcing** сообществу

**Cosmic Python использует современную интерпретацию DDD**, которая **расширяет** Эванса.

### Что добавляет Cosmic Python:

```python
# Domain Event — факт, который произошёл
@dataclass
class OutOfStock(Event):
    sku: str

# Модель публикует события
class Product:
    def allocate(self, line):
        if not self.can_allocate(line):
            self.events.append(OutOfStock(line.sku))  # НЕ исключение!
            return None

# Обработчики реагируют на события
def send_out_of_stock_notification(event, uow):
    email.send(f"Товар {event.sku} закончился")
```

#### 🧒 Для школьника:

**Domain Event** — как **объявление по громкой связи в школе**: "Внимание! Завтра отменяется первая пара!".

- Учитель (доменная модель) **не бегает** по классам, чтобы сообщить каждому
- Он просто делает объявление
- Кто услышал — отреагировал (ученики поспали подольше, родители обрадовались)
- Кто не услышал — ничего страшного, объявление всё равно прозвучало

## 🔷 Глава 11: Microservices через события — корни у Эванса (Ch 14)

### Что говорит Cosmic Python:
Интеграция микросервисов через события убирает временную связность.

### 🌳 Глубинные корни у Эванса:

**Chapter 14: Maintaining Model Integrity** — Эванс вводит **Bounded Context** и **Context Map** — фундамент для микросервисов!

#### 🎓 Для разработчика — паттерны отношений между контекстами:

```
┌─────────────────┐
│  SHARED KERNEL  │  — два сервиса разделяют часть модели
└─────────────────┘

┌──────────────────┐
│ CUSTOMER/SUPPLIER│  — один сервис обслуживает другой
└──────────────────┘

┌─────────────────┐
│   CONFORMIST    │  —下游 сервис подстраивается под upstream
└─────────────────┘

┌──────────────────────┐
│ ANTICORRUPTION LAYER │  — защитный слой от "чужой" модели
└──────────────────────┘

┌─────────────────┐
│  SEPARATE WAYS  │  — сервисы вообще не интегрируются
└─────────────────┘

┌─────────────────┐
│ OPEN HOST SERVICE│  — публичный API для многих клиентов
└─────────────────┘

┌─────────────────┐
│PUBLISHED LANGUAGE│ — общий язык обмена (XML schema, protobuf)
└─────────────────┘
```

**Anti-Corruption Layer (ACL)** — один из самых важных паттернов Эванса:

```python
# Проблема: чужая модель "загрязняет" нашу
# Решение: слой перевода

class ExternalPaymentGateway:
    def pay(self, amount, currency, customer_id):
        # Внешний API со своей странной моделью
        ...

class PaymentService:  # Наш ACL
    def process_payment(self, order: Order):
        # Переводим нашу модель в их термины
        external_request = {
            'amt': order.total.amount,
            'cur': order.total.currency.code,
            'cust_ref': order.customer.external_id
        }
        result = self.gateway.pay(**external_request)
        # Переводим их ответ обратно в нашу модель
        return PaymentConfirmation.from_external(result)
```

#### 🧒 Для школьника:

**Bounded Context** — как **разные страны со своими языками**:

- В России говорят "спасибо"
- В Англии — "thank you"
- Во Франции — "merci"

Это **одно и то же понятие**, но в **разных контекстах** оно звучит по-разному.

**Anti-Corruption Layer** — как **переводчик на границе**. Когда ты едешь из России в Китай, ты не начинаешь думать иероглифами. Ты берёшь переводчика, который:
1. Слушает тебя (понимает твою модель)
2. Говорит с китайцами (знает их модель)
3. Переводит обратно

Без переводчика (ACL) ты начнёшь **портить свой язык**, пытаясь говорить на чужом.

## 🔷 Глава 12: CQRS — частично у Эванса (Ch 4)

### Что говорит Cosmic Python:
Разделяй чтение и запись.

### 🌳 Глубинные корни у Эванса:

Эванс не описывает CQRS явно (паттерн появился позже у **Greg Young**, 2010), но его идея **изоляции доменного слоя** (Ch 4) — это основа CQRS.

**Инсайт Эванса:** Модель, оптимизированная для бизнес-правил, часто **плохо подходит** для сложных запросов.

```python
# Запись через доменную модель (сложная, с правилами)
def allocate(cmd, uow):
    with uow:
        product = uow.products.get(cmd.sku)
        product.allocate(line)  # проверяет лимиты, инварианты
        uow.commit()

# Чтение через оптимизированную модель (простая, быстрая)
def get_allocations(orderid):
    return db.execute("""
        SELECT sku, batchref, qty 
        FROM allocations_view 
        WHERE orderid = :orderid
    """)
```

#### 🧒 Для школьника:

**CQRS** — как **два разных способа пользоваться библиотекой**:

- **Сдать книгу** (запись) — идёшь к библиотекарю, он проверяет состояние книги, ставит штамп, заносит в журнал. Долго, но правильно.
- **Найти книгу** (чтение) — идёшь к каталогу, смотришь карточку. Быстро, но каталог может **немного отставать** от реальности (кто-то только что взял книгу, а в каталоге ещё написано "на полке").

# 📚 ЧАСТЬ 2: ПОЛНЫЙ ПЕРЕСКАЗ КНИГИ ЭРИКА ЭВАНСА "DOMAIN-DRIVEN DESIGN"

## 🏛️ ЧАСТЬ I: Модель в действии (Ch 1-4)

### 📖 Chapter 1: Crunching Knowledge (Переваривание знаний)

**Главная идея:** Модель рождается в диалоге разработчиков и экспертов.

**Пример с PCB (печатными платами):**
- Разработчик ничего не знал об электронике
- Эксперты говорили на своём жаргоне: "nets", "pins", "topology"
- Через **множество итераций** они вместе создали модель
- **Ключевой момент:** Модель развивалась вместе с пониманием

**Инсайты:**
1. **Knowledge Crunching** — это не одноразовый сбор требований, а **постоянный процесс**
2. **Прототипы** помогают экспертам увидеть модель в действии
3. **Сценарии** (walkthroughs) выявляют пробелы в модели

#### 🧒 Для школьника:

Представь, что ты делаешь **компьютерную игру про зоопарк**, но никогда не был в зоопарке. Ты идёшь к **смотрителю** и начинаешь расспрашивать:
- "Чем кормят львов?"
- "Как часто нужно убирать вольер?"
- "Что делать, если животное заболело?"

Сначала ты делаешь **простую версию** игры. Показываешь смотрителю. Он говорит: "Нет, львов нельзя кормить рыбой, они едят мясо!" Ты исправляешь. Показываешь снова. "А где ветеринар? Когда животное болеет, его нужно лечить!"

**Через 10 таких циклов** у тебя получается игра, которая **по-настоящему отражает** работу зоопарка. Это и есть **Knowledge Crunching**.

### 📖 Chapter 2: Communication and the Use of Language

**Главная идея:** **Ubiquitous Language** (Вездесущий Язык) — язык модели, на котором говорят **все**: разработчики, эксперты, менеджеры.

**Правила Эванса:**
1. Используй термины модели **везде** — в коде, в разговорах, в документации
2. Если термин неудобен — **меняй модель**, а не придумывай новый термин
3. **Modeling Out Loud** — проговаривай сценарии вслух, используя термины модели

**Пример плохой коммуникации:**
```
Эксперт: "Нам нужно изменить точку таможенной очистки"
Разработчик: "Окей, удалим строки из таблицы shipment, 
             передадим новые параметры в RoutingService..."
Эксперт: "??? Какие строки? Какая таблица?"
```

**Пример хорошей коммуникации (Ubiquitous Language):**
```
Эксперт: "Нужно изменить точку таможенной очистки"
Разработчик: "Окей, изменим RouteSpecification, 
             тогда Itinerary перегенерируется автоматически"
Эксперт: "Да, именно так!"
```

#### 🧒 Для школьника:

Представь, что вы с друзьями придумали **свой секретный язык** для игры в шпионов:
- "Агент" — это игрок
- "Миссия" — это задание
- "База" — это место сбора

Когда вы играете, вы **не говорите** "Вася, иди к дереву". Вы говорите: "**Агент Иванов, следуй на Базу**".

Этот язык:
- **Понятен всем** в команде
- **Точнее** обычного языка
- **Связан** с самой игрой

**Ubiquitous Language** в программировании — это то же самое. Когда все говорят на одном языке, misunderstandings исчезают.

### 📖 Chapter 3: Binding Model and Implementation

**Главная идея:** Модель **должна быть** в коде. Нет "отдельной аналитической модели" и "отдельной реализации".

**Проблема, которую описывает Эванс:**
- Аналитики создают "красивую" модель на бумаге
- Разработчики пишут код, который **не соответствует** модели
- Возникает **"смертельный разрыв"** между анализом и реализацией

**Решение: MODEL-DRIVEN DESIGN**
- Каждый объект в коде — это **концепция из модели**
- Изменение кода = изменение модели
- **Hands-on modelers** — архитекторы должны писать код!

**Пример с PCB layout (стр. 30-33):**
- Инженеры использовали **скрипты** для обхода ограничений программы
- Скрипты манипулировали файлами через сортировку и regex
- **Model-Driven Design** ввёл понятие **Bus** (группа цепей) как явную сущность
- Код стал **прозрачным** и понятным

#### 🧒 Для школьника:

Представь, что ты **архитектор**, который нарисовал красивый дом. Но строители построили **совсем другой дом**, потому что "так было удобнее".

**Эванс говорит:** Архитектор должен **сам класть кирпичи**, хотя бы иногда. Только так он поймёт, что его чертежи **реально работают**.

В программировании: **тот, кто проектирует модель, должен писать код**. Иначе модель станет "красивой картинкой на стене", которую никто не использует.

### 📖 Chapter 4: Isolating the Domain

**Главная идея:** **Layered Architecture** — отделяй доменную логику от всего остального.

```
┌─────────────────────┐
│  User Interface     │  ← Кнопки, формы
├─────────────────────┤
│  Application Layer  │  ← Use cases (оркестрация)
├─────────────────────┤
│  Domain Layer       │  ← БИЗНЕС-ЛОГИКА (сердце!)
├─────────────────────┤
│  Infrastructure     │  ← БД, email, API
└─────────────────────┘
```

**Правила:**
- Domain Layer **не зависит** ни от кого сверху
- Application Layer **только координирует**, не содержит бизнес-правил
- Infrastructure **обслуживает** верхние слои через интерфейсы

**Smart UI "Anti-Pattern"** (стр. 44):
Эванс описывает **анти-паттерн**, когда вся логика в UI. Это работает для простых CRUD-приложений, но **не масштабируется**.

#### 🧒 Для школьника:

**Layered Architecture** — как **организация кухни в ресторане**:

- **Зал (UI)** — где гости. Официанты принимают заказы.
- **Раздача (Application)** — официанты относят заказы на кухню, забирают готовые блюда.
- **Кухня (Domain)** — повара готовят. Это **сердце ресторана**!
- **Подсобка (Infrastructure)** — холодильники, плиты, водопровод.

**Важно:** Повар **не должен** бегать в зал и принимать заказы. Официант **не должен** лезть в кастрюлю. Каждый делает своё дело.

## 🏗️ ЧАСТЬ II: Строительные блоки (Ch 5-6)

### 📖 Chapter 5: A Model Expressed in Software

Эванс описывает **фундаментальные строительные блоки**:

#### 1. **ENTITIES** (Сущности)

Определяются **идентичностью**, а не атрибутами.

```python
class Person:  # ENTITY
    def __init__(self, id, name, address):
        self.id = id  # Идентичность!
        # Даже если name и address изменятся — это тот же Person
```

**Правила Эванса:**
- Идентичность должна **прослеживаться во времени**
- Идентификатор может быть **внутренним** (UUID) или **внешним** (паспорт)
- **Не присваивай идентичность объектам, которые в ней не нуждаются!**

#### 2. **VALUE OBJECTS** (Объекты-значения)

Определяются **только атрибутами**. **Не имеют идентичности**.

```python
@dataclass(frozen=True)
class Money:  # VALUE OBJECT
    amount: Decimal
    currency: str
    
    # Две Money(100, 'RUB') РАВНЫ
    # Можно свободно копировать, шарить
```

**Правила Эванса:**
- **ВСЕГДА делай их immutable** (неизменяемыми)
- Можно **свободно шарить** между объектами
- **Не присваивай им ID** — это бессмысленно

**Пример Эванса:** Адрес может быть **Entity или Value** в зависимости от контекста:
- Для **почтовой службы** — Entity (нужно отслеживать)
- Для **интернет-магазина** — Value (просто атрибут клиента)

#### 3. **SERVICES** (Сервисы)

Операции, которые **не принадлежат** ни одной сущности.

```python
class FundsTransferService:  # Domain Service
    def transfer(self, from_account, to_account, amount):
        # Операция涉及 два Account — кому она принадлежит?
        # Никому! Это отдельный SERVICE
        from_account.debit(amount)
        to_account.credit(amount)
```

**Правила Эванса:**
- Service — это **глагол**, а не существительное
- **Stateless** (не имеет состояния)
- Интерфейс определяется **в терминах модели**
- **Не злоупотребляй** — не выноси туда всё подряд!

#### 4. **MODULES** (Пакеты)

Группировка связанных концепций.

**Правила Эванса:**
- Имена модулей — **часть Ubiquitous Language**
- **High cohesion, low coupling**
- Модули должны **рассказывать историю** модели

#### 🧒 Для школьника:

**Entity** — как **твой любимый плюшевый мишка**. Даже если ему оторвали ухо и пришили обратно, это **тот же самый мишка**. У него есть "душа" (идентичность).

**Value Object** — как **конфета M&M's**. Тебе всё равно, **какая именно** красная конфета у тебя во рту. Все красные M&M's одинаковые. Если одна потерялась, ты берёшь другую — и не расстраиваешься.

**Service** — как **арбитр в футболе**. Он не игрок ни одной команды. Он просто обеспечивает **соблюдение правил** во время игры.

### 📖 Chapter 6: The Life Cycle of a Domain Object

Три ключевых паттерна:

#### 1. **AGGREGATES** (Агрегаты)

**Самый важный паттерн книги!**

```
┌─────────────────────────────────┐
│         AGGREGATE               │
│  ┌─────────────────────────┐    │
│  │  Aggregate Root (Entity)│◄───┼── Только на него могут
│  │  ┌───────────────────┐  │    │    ссылаться внешние объекты
│  │  │  Internal Entity  │  │    │
│  │  └───────────────────┘  │    │
│  │  ┌───────────────────┐  │    │
│  │  │  Value Object     │  │    │
│  │  └───────────────────┘  │    │
│  └─────────────────────────┘    │
└─────────────────────────────────┘
```

**Пример с Purchase Order (стр. 77-81):**
- PO (Purchase Order) — **Aggregate Root**
- Line Items — **внутренние Entities**
- Part (товар) — **отдельный Aggregate**

**Проблема:** Если два пользователя одновременно добавляют Line Items в один PO, инвариант "сумма ≤ лимит" может нарушиться.

**Решение:** Блокировать **весь PO**, а не отдельные строки. Но Part (товар) **не блокируем** — он в другом агрегате.

**Инсайт Эванса:** Цена Part **копируется** в Line Item при создании. Если цена Part изменится позже, **старые PO не меняются**. Это отражает **реальность бизнеса**: заказ, сделанный вчера, имеет **вчерашние цены**.

#### 2. **FACTORIES** (Фабрики)

**Инкапсулируют сложное создание объектов.**

```python
class OrderFactory:
    def create_order(self, customer, items) -> Order:
        # Сложная логика создания:
        # - Проверка кредитного лимита
        # - Применение скидок
        # - Создание Line Items
        # - Установка начального статуса
        order = Order(id=generate_id())
        # ... много логики
        return order
```

**Правила Эванса:**
- Фабрика должна **создавать объект в валидном состоянии**
- Фабрика **может знать** о внутренней структуре объекта
- **ENTITY Factory** присваивает ID
- **VALUE Factory** возвращает готовый immutable объект

#### 3. **REPOSITORIES** (Репозитории)

**Инкапсулируют хранение и поиск.**

**Правила Эванса:**
- Repository **только для Aggregate Roots**
- Клиент видит **коллекцию в памяти**
- Repository **не должен** содержать бизнес-логику
- **Отделение от Factories**: Repository находит **старые** объекты, Factory создаёт **новые**

#### 🧒 Для школьника:

**Aggregate** — как **семья с семейным бюджетом**:
- **Папа (Root)** — принимает решения о тратах
- **Мама и дети** — могут тратить, но в рамках бюджета
- **Семейное правило:** "нельзя тратить больше, чем зарабатываем"
- Если семья покупает холодильник, **все члены семьи** "участвуют" в этой покупке
- Соседи (другие агрегаты) не могут напрямую сказать маме: "купи мне хлеба". Они говорят **папе**.

**Factory** — как **родильный дом**:
- Ты не сам "делаешь" ребёнка — это сложный процесс
- Родильный дом **обеспечивает**, что ребёнок рождается **здоровым** (со всеми нужными атрибутами)
- Ребёнок получает **свидетельство о рождении** (ID)

**Repository** — как **архив документов**:
- Ты говоришь: "Дайте мне договор №123"
- Архивариус идёт, находит, приносит
- Тебе не нужно знать, **где** он хранится и **как** организован архив

## 🔮 ЧАСТЬ III: Рефакторинг к озарению (Ch 7-13)

### 📖 Chapter 7-8: Breakthrough (Прорыв)

**Главная идея:** Истинное понимание приходит **внезапно**, после долгой работы.

**Пример Эванса (стр. 122-127):** Система синдицированных кредитов.

**Проблема:** Команда долго мучилась с моделью, где "доли в Facility" и "доли в Loan" были **жёстко связаны**. Это приводило к ошибкам округления и сложному коду.

**Прорыв:** Однажды они поняли, что **доли могут меняться независимо**! Facility определяет **потенциал**, Loan — **фактическое использование**.

**Результат:** Появилась концепция **Share Pie** (Пирог долей) — абстракция, которая:
- Упростила код **в разы**
- Убрала **все** ошибки округления
- Стала **частью Ubiquitous Language** — бизнес-эксперты использовали её в разговорах

#### 🧒 Для школьника:

Представь, что ты решаешь **очень сложную задачу по математике**. Ты бьёшься над ней час, два, три... Ничего не получается!

И вдруг, **на прогулке**, тебя **осеняет**: "Ага! Нужно посмотреть на задачу **с другой стороны**!"

Ты возвращаешься, переписываешь решение — и оно становится **простым и красивым**. Это и есть **Breakthrough**.

**Важно:** Breakthrough **нельзя запланировать**. Он приходит **после долгой работы**. Но когда приходит — всё меняется.

### 📖 Chapter 9: Making Implicit Concepts Explicit

**Главная идея:** Ищи **скрытые концепции** в коде и делай их явными.

**Признаки скрытой концепции:**
1. Сложная логика в методе
2. Странные имена ("processData", "handleStuff")
3. Множество параметров
4. Комментарии, объясняющие "что здесь происходит"

**Пример с начислением процентов (стр. 133-135):**
- Было: сложный `InterestCalculator` с кучей условий
- Стало: явные концепции **Accrual** (начисление) и **Payment** (оплата)
- Код стал **декларативным** и понятным

**Техники поиска:**
1. **Listen to Language** — слушай, какие слова используют эксперты
2. **Scrutinize Awkwardness** — исследуй "неуклюжие" места в коде
3. **Contemplate Contradictions** — размышляй над противоречиями
4. **Read the Book** — читай книги по предметной области!

#### 🧒 Для школьника:

Представь, что ты пишешь **сочинение**. Ты написал предложение:

> "Я пошёл туда и сделал то, и потом ещё кое-что, и получилось хорошо."

Учитель говорит: "**Что** 'туда'? **Что** 'то'? Используй **конкретные слова**!"

Ты переписываешь:

> "Я пошёл **в библиотеку**, **взял книгу** о динозаврах, **прочитал** главу о тираннозаврах, и **узнал** много интересного."

**Теперь** понятно, что произошло! Ты сделал **скрытые концепции явными**.

### 📖 Chapter 10: Supple Design (Податливый дизайн)

**Главная идея:** Дизайн должен быть **приятным в работе**, лёгким для изменения.

**Ключевые паттерны:**

#### 1. **Intention-Revealing Interfaces**

```python
# ПЛОХО: непонятно, что делает
def paint(p: Paint):
    self.v += p.v
    # ... 50 строк магии

# ХОРОШО: ясно, что происходит
def mix_in(self, other_paint: Paint):
    # Смешивает краски, возвращает новый цвет
```

#### 2. **Side-Effect-Free Functions**

```python
# Чистая функция — безопасна
def add(a, b):
    return a + b  # Никаких побочных эффектов!

# Можно вызывать сколько угодно раз — результат тот же
```

#### 3. **Assertions** (Инварианты, пре/пост-условия)

```python
class Account:
    def withdraw(self, amount):
        # Precondition:
        assert amount > 0
        assert amount <= self.balance
        
        self.balance -= amount
        
        # Postcondition:
        assert self.balance >= 0
```

#### 4. **Closure of Operations** (Замкнутость операций)

```python
class Money:
    def add(self, other: 'Money') -> 'Money':
        # Money + Money = Money (замкнуто!)
        return Money(self.amount + other.amount, self.currency)
    
    def multiply(self, factor: float) -> 'Money':
        # Money * number = Money (почти замкнуто)
        return Money(self.amount * factor, self.currency)
```

**Пример с Share Pie (стр. 184-186):**
```python
class SharePie:
    def plus(self, other: 'SharePie') -> 'SharePie':
        # Сложить два пирога — получаем новый пирог
        ...
    
    def minus(self, other: 'SharePie') -> 'SharePie':
        # Вычесть — тоже пирог
        ...
    
    def prorated(self, amount) -> 'SharePie':
        # Распределить сумму пропорционально — пирог
        ...
```

Это позволяет писать **декларативный код**:
```python
# Бизнес-транзакция как математическое выражение
deviation = actual.minus(original_agreement)
new_loan = old_loan.plus(drawdown_shares)
```

#### 🧒 Для школьника:

**Supple Design** — как **хорошо заточенный карандаш**:
- Легко писать (использовать)
- Легко точить (изменять)
- Не ломается в руках (надёжный)

**Intention-Revealing Interface** — как **подпись на коробке**:
- Вместо "Коробка №47" написано "Зимние игрушки"
- Сразу понятно, что внутри!

**Side-Effect-Free Function** — как **честный продавец**:
- Ты даёшь ему 100 рублей, он даёт тебе шоколадку
- Он **не делает** ничего больше: не ворует у тебя из кармана, не подписывает тебя на рассылку
- Ты можешь **доверять** ему и ходить к нему снова

### 📖 Chapter 13: Refactoring Toward Deeper Insight

**Главная идея:** Рефакторинг — это **не только** про код, но и про **понимание домена**.

**Три фокуса:**
1. **Live in the domain** — живи в предметной области
2. **Keep looking at things a different way** — смотри под разными углами
3. **Maintain an unbroken dialog with domain experts** — постоянно общайся с экспертами

**Когда рефакторить:**
- Дизайн **не отражает** текущее понимание домена
- Важные концепции **скрыты** (implicit)
- Видна возможность сделать дизайн **более податливым**

**Crisis as Opportunity (стр. 209):**
Эванс ссылается на теорию **punctuated equilibrium** (прерывистое равновесие):
- Долгие периоды **постепенного улучшения**
- Короткие **взрывы прорывов**
- Новое **равновесие**

**Важно:** Breakthrough **нельзя запланировать**, но можно **подготовить почву** для него.

## 🗺️ ЧАСТЬ IV: Стратегический дизайн (Ch 14-17)

### 📖 Chapter 14: Maintaining Model Integrity

**Самая важная глава для микросервисов!**

#### BOUNDED CONTEXT (Ограниченный контекст)

**Главная идея:** Одна модель **не может** охватить всю организацию. Нужно **явно определять границы**.

```
┌─────────────────┐  ┌─────────────────┐
│  Booking Context │  │  Routing Context│
│  (Бронирование)  │  │  (Маршруты)     │
│                 │  │                 │
│  Cargo = то, что│  │  Cargo = узел   │
│  нужно доставить│  │  в графе        │
│                 │  │                 │
│  Customer = кто │  │  Customer = ??? │
│  заказал        │  │  (не нужен!)    │
└─────────────────┘  └─────────────────┘
```

**Инсайт Эванса:** Одно и то же слово **может означать разное** в разных контекстах!
- В контексте **продаж**: "Product" = то, что мы продаём, с ценой, описанием
- В контексте **склада**: "Product" = то, что лежит на полке, с весом, размером
- В контексте **доставки**: "Product" = то, что нужно перевезти, с габаритами

#### CONTEXT MAP (Карта контекстов)

**Визуализация отношений между контекстами:**

```
         ┌──────────────┐
         │   Billing    │
         └──────┬───────┘
                │ Customer/Supplier
         ┌──────▼───────┐
         │   Booking    │◄────────────┐
         └──────┬───────┘             │
                │ Shared Kernel       │ Conformist
         ┌──────▼───────┐             │
         │   Routing    │             │
         └──────────────┘             │
                               ┌──────▼───────┐
                               │   Legacy     │
                               │   System     │
                               └──────────────┘
```

#### Паттерны отношений:

**1. SHARED KERNEL (Общее ядро)**
- Два контекста разделяют **часть модели**
- Изменения требуют **консультаций**
- Частая интеграция

**2. CUSTOMER/SUPPLIER (Заказчик/Поставщик)**
- Upstream (поставщик) **обслуживает** downstream (заказчика)
- Downstream **участвует в планировании** upstream
- **Автоматические acceptance tests** обязательны!

**3. CONFORMIST (Конформист)**
- Downstream **полностью подстраивается** под upstream
- Нет возможности влиять на upstream
- Используется, когда:
  - Upstream — **очень качественный**
  - Интеграция **очень тесная**
  - Downstream **маленький**

**4. ANTICORRUPTION LAYER (Антикоррупционный слой)**
- **Защитный слой** между контекстами
- Переводит **чужую модель** в **нашу**
- Используется, когда:
  - Чужая модель **плохого качества**
  - Чужая модель **не подходит** нам
  - Мы хотим **изолировать** нашу модель

**5. SEPARATE WAYS (Разные пути)**
- Контексты **вообще не интегрируются**
- Используй, когда интеграция **не даёт ценности**

**6. OPEN HOST SERVICE (Открытый сервис)**
- Публичный API для **многих** клиентов
- Стандартизированный протокол

**7. PUBLISHED LANGUAGE (Опубликованный язык)**
- Общий язык обмена (XML Schema, Protobuf, JSON Schema)
- **Независимые интерпретации** совместимы

#### 🧒 Для школьника:

**Bounded Context** — как **разные предметы в школе**:

- На **физике** "работа" = сила × расстояние (Джоули)
- На **литературе** "работа" = сочинение на 5 страниц
- На **труде** "работа" = скворечник, который ты сделал

**Одно и то же слово**, но **разные значения** в разных контекстах. Если ты попытаешься использовать определение из физики на литературе, учитель **посмеётся**.

**Context Map** — как **расписание уроков**: оно показывает, **когда** и **где** ты используешь **какое значение** слова.

**Anticorruption Layer** — как **переводчик**, когда к вам в школу приехал **иностранный ученик**. Он говорит "work", а ты должен понять, что он имеет в виду — в **его** контексте.

### 📖 Chapter 15: Distillation (Дистилляция)

**Главная идея:** Выдели **самое важное** — **CORE DOMAIN**.

#### Виды доменов:

```
┌────────────────────────────────────────┐
│           CORE DOMAIN                  │
│   То, что отличает нас от конкурентов  │
│   Наши "секретные рецепты"             │
│   Самые сильные разработчики здесь!    │
├────────────────────────────────────────┤
│      SUPPORTING SUBDOMAINS             │
│   Нужно для бизнеса, но не уникально   │
│   Можно отдать на аутсорс              │
├────────────────────────────────────────┤
│       GENERIC SUBDOMAINS               │
│   Стандартные вещи (аутентификация,    │
│   бухгалтерия, отчёты)                 │
│   КУПИ или используй open source!      │
└────────────────────────────────────────┘
```

#### Паттерны дистилляции:

**1. DOMAIN VISION STATEMENT**
- Короткий документ (1 страница)
- Описывает **ценность** CORE DOMAIN
- **Не содержит** технических деталей

**2. HIGHLIGHTED CORE**
- **Выделение** CORE в коде/документации
- Может быть:
  - Отдельный документ
  - Помеченные классы (стереотипы)
  - Отдельный пакет

**3. SEGREGATED CORE**
- Вынести CORE в **отдельные модули**
- Очистить от "примесей"

**4. ABSTRACT CORE**
- Выделить **самые фундаментальные** концепции
- Часто — **интерфейсы** между модулями

**5. GENERIC SUBDOMAIN**
- Вынести **стандартные** вещи **из** CORE
- Варианты реализации:
  - Off-the-shelf (купить)
  - Published model (из книги)
  - Outsourced (заказать)
  - In-house (сделать самим, но **не лучшими** разработчиками!)

**Пример с Time Zones (стр. 262-263):**
- **Shipping проект**: Нужна сложная логика часовых поясов → сделали сами, но **контрактником** (не ключевым разработчиком)
- **Insurance проект**: Не была нужна сложная логика, но **ключевые разработчики** потратили недели на "универсальное решение" → **потерянное время**

**Инсайт:** Лучшие разработчики должны работать над **CORE DOMAIN**, а не над Generic Subdomains!

#### 🧒 Для школьника:

**Distillation** — как **приготовление эссенции**:

Ты делаешь **вишнёвый компот**:
1. Берёшь вишню, воду, сахар
2. Варишь
3. **Процеживаешь** — отделяешь жидкость от косточек и кожуры
4. Получаешь **концентрированный вкус вишни**

**CORE DOMAIN** — это **концентрат вишни**. Это то, ради чего всё делается.
**GENERIC SUBDOMAINS** — это **вода и сахар**. Они нужны, но их можно **купить** в любом магазине.
**SUPPORTING SUBDOMAINS** — это **красивый стакан**, в который ты наливаешь компот. Важно, но **не уникально**.

### 📖 Chapter 16: Large-Scale Structure (Крупномасштабная структура)

**Главная идея:** Когда система **очень большая**, нужна **общая структура** для координации.

#### Паттерны:

**1. EVOLVING ORDER (Эволюционирующий порядок)**
- Структура **растёт вместе** с системой
- **Не замораживай** решения в начале!
- **Минимализм** — лучше меньше, да лучше

**2. SYSTEM METAPHOR (Системная метафора)**
- **Аналогия**, которая направляет дизайн
- Пример: "firewall" для сетевой безопасности
- **Опасно:** метафора может **ограничить** мышление

**3. RESPONSIBILITY LAYERS (Слои ответственности)**

```
┌─────────────────────┐
│   Decision Support  │  ← Что делать? (рекомендации)
├─────────────────────┤
│      Policy         │  ← Правила, цели
├─────────────────────┤
│     Operations      │  ← Что происходит сейчас
├─────────────────────┤
│     Potential       │  ← Что мы можем (ресурсы)
└─────────────────────┘
```

**Пример из shipping (стр. 287-293):**
- **Capability/Potential**: Transit Leg, Ship, Customer
- **Operations**: Cargo, Itinerary, Route Specification
- **Decision Support**: Router, Route Bias Policy

**4. KNOWLEDGE LEVEL (Уровень знаний)**

**Идея:** Разделить **"что есть"** и **"правила"**.

```
┌─────────────────────────┐
│    KNOWLEDGE LEVEL      │
│  Employee Type          │  ← Правила
│  - "Manager"            │
│  - "Developer"          │
└───────────┬─────────────┘
            │ определяет
┌───────────▼─────────────┐
│    OPERATIONS LEVEL     │
│  Employee               │  ← Конкретные объекты
│  - Иван (Manager)       │
│  - Пётр (Developer)     │
└─────────────────────────┘
```

**5. PLUGGABLE COMPONENT FRAMEWORK**
- **Ядро** с интерфейсами
- **Компоненты** реализуют интерфейсы
- Используется в **зрелых** системах
- **Опасно:** может **заморозить** эволюцию модели

#### 🧒 Для школьника:

**Large-Scale Structure** — как **правила строительства города**:

Без правил каждый строит **как хочет** — получается хаос:
- Дом посреди дороги
- Завод рядом со школой
- Парк без дорог

С правилами (зонирование):
- **Жилая зона** — дома
- **Промышленная зона** — заводы
- **Парковая зона** — отдых

**Responsibility Layers** — как **этажи в доме**:
- **Подвал** — фундамент, коммуникации (Potential)
- **Первый этаж** — магазин, офисы (Operations)
- **Второй этаж** — квартиры (Policy)
- **Чердак** — место для размышлений (Decision Support)

## 🚀 Ключевые инсайты из обеих книг

### 1. **Модель — это сердце системы** (Эванс)
- **Не** "база данных с бизнес-логикой сверху"
- **Не** "набор CRUD-операций"

- Микросервисы — это **техническая реализация** Bounded Contexts

### 4. **Events — это расширение DDD** (Cosmic Python)
- Эванс (2003) почти не говорит о событиях

- Cosmic Python показывает, как **интегрировать** события с классическим DDD

### 5. **Простота — результат тяжёлой работы** (Эванс Ch 10)
- Supple Design **не возникает** сам по себе
- Это результат **множества рефакторингов**
- **Breakthrough** приходит после **долгой работы**

5. **Простые тесты** = **хорошая архитектура**

### Для архитектора:

1. **Пиши код!** (Эванс Ch 3) — архитектор, не пишущий код, бесполезен
2. **Минимализм** (Эванс Ch 17) — меньше структуры = больше свободы
3. **Эволюция** (Эванс Ch 16) — не замораживай решения
4. **Feedback loop** (Cosmic Python Ch 5) — тесты как источник инсайтов
